# ADR-0011 — H3 available as a derived index, never as geometry

**Status**: accepted

## Context

`h3-pg` 4.5.0 was built from source and installed for PostgreSQL 18. H3 is
genuinely useful for spatial bucketing, aggregation across datasets whose
geometries do not align, and multi-resolution analytics.

It is also easy to misuse. An H3 cell is a hexagon covering an area; a country
is not a hexagon. Storing a set of cells as if it were a boundary loses the
boundary.

## Decision

The `h3` extension is available and may be used to build **derived** spatial
indexes — materialised views over canonical geometry, refreshable, disposable.

It is never canonical geometry. `geo.feature_version.geom` holds real geometry
in EPSG:4326 and is the only authoritative spatial representation. No canonical
table has an H3 column.

`h3_postgis` is **not** installed: it hard-requires `postgis_raster`, which is a
real dependency for a set of bridge functions this system does not need. Core
`h3` provides `h3_lat_lng_to_cell` and the cell arithmetic, which is what a
derived index requires; the check that this is sufficient was run before
deciding.

## If it is used

Any derived H3 table must document the resolution and why, the precision
trade-off at that resolution, and be reproducible by a refresh. Cells are an
index into geometry, not a substitute for it.

## Consequences

- Available without being load-bearing. Dropping the extension would lose a
  derived view, never a fact.
- `postgis_raster` stays out of the database.

## What would reverse this

Nothing about the boundary between derived and canonical. The extension's
*usage* will expand when there are enough geometries for spatial bucketing to
be worth building — at present `geo.feature_version` is empty, because no
boundary dataset has been ingested.
